# 00 开发总纲 — DSH Mobile（手机远程操作端）
> 版本：v2.4.0 · 状态：已开源发布，持续维护 · 本文件是后续全部工作的最高依据
## 1. 项目一句话

**把 dsh（DeepSeek Harness）变成随身控制台**：手机随时查看 agent 状态、发消息派活、审批决策、接收完成/待回答/失败通知、管理会话——电脑端跑着，人不在电脑前也能全程操作。

## 3. 设计定稿（界面冻结，开发必须遵守）

- **视觉**：DeepSeek 品牌配色（主色 `#426EFE`，深色 `#0E1116`）、衬线大标题、1.5 线宽线性图标、大圆角、默认跟随系统深浅色
- **信息架构**：侧边栏三项（首页 / 会话 / 设置）；对话、通知为详情页；无底部 tab
- **首页固定欢迎界面**（不做状态切换）：欢迎语 + 最近会话 + 新建会话 + 输入权限
- **新建会话当场选模式**（标准 PTC/极简/创造，预设 · 设置默认值）
- **所有展示数据真实对齐 PC 端**：模型（deepseek-v4-flash / deepseek-v4-pro）、推理强度（off/high/max）、权限（read-only / workspace-write / danger-full-access，Full Access 需风险确认）、模式显示名（标准 PTC/极简/创造）
- **诚实原则**：未实现的功能明确标注「开发中」，不出现无声摆设；深色模式默认跟随系统
- **移动端不感知插件**：核心层只依赖 dsh 内核语义；动作区（可选）打开时实时拉取清单；插件管理永远在 PC 端
## 4. 开发阶段（依赖顺序）
> 现状（v2.4.0）：Phase 1-3 全部完成；网页版已移除（见 Phase 3 注）；v2.2~v2.4 补充：消息操作/上下文圆环/归档对齐、通知删除、问询/审批弹窗、微信式无限上翻、兼容性硬化（详见 CHANGELOG）。
### Phase 1：后端 API 补全（完成 ✅）

**范围**：插件新增移动端所需的全部 API。
| 交付版 | 验收标准 |
|---|---|
| 模型目录 API（读取） | 返回 PC 端真实模型 + 推理强度选项与当前值 |
| 会话配置 API（读写） | 切换当前会话模型/推理强度/权限预设；风险确认后允许 danger-full-access |
| Agent 预设 API（读写） | 读默认预设；新建会话带预设参数 |
| 新建会话 API | 按 preset 创建会话，返回 id 可续接 |
| 通知中心 API | 聚合完成/待回答/失败事件；未读 已读状态 |
| 动作区契约 v0.1 | GET 动作清单 + POST 执行（注册服务 `ctx.mobileActions`） |

**Phase 1 完成标志**：API 全链路可用（e2e-check 通过）。
### Phase 2：推送桥（完成 ✅）

**范围**：agent 完成 / 需要回答 / 失败三类事件 → 推送服务（Bark / Serverchan / ntfy，可配置）→ 手机系统通知；App 在后台也能收到。
| 交付版 | 验收标准 |
|---|---|
| 推送桥配置（profile settings） | 配置推送服务 URL + 开关 + 事件类型选择 |
| 事件 → 推送转发 | 三类事件触发推送，内容含会话摘要；同会话同类型聚合 |

**Phase 2 完成标志**：手机锁屏收到任务完成/需要回答通知。
### Phase 3：Flutter App（完成 ✅）

**范围**：按定稿原型实现原生 App，对接 Phase 1 API。
| 交付版 | 验收标准 |
|---|---|
| Flutter 工程（Android 优先） | 全部界面与弹窗按原型实现 |
| 连接管理 | 扫码/手动连接、重连、断线提示 |
| 通知接入 | 前台 SSE + 后台依赖 Phase 2 推送桥 |
| 打包 | Android APK 可安装 |

**Phase 3 完成标志**：APK 安装后全功能可用，体验等于原型。
> **v2.1 决策**：网页版（`/m` 页面）在 App 完成后移除（不再提供浏览器形态），减少运行资源；桌面设置页由客户端模块（`client.js`）提供扫码入口。
## 5. 阶段依赖与顺序理顺
1. **API 先行**：App 与脚本测试共用同一套 API，先写 API 再写客户端
2. **推送桥在 App 前**：App 的后台通知直接复用推送桥，不必在 Flutter 里重做
3. **App 最后**：纯锦上添花，风险最低的部分最后做

## 6. 关键决策记录（ADR 摘要）
| # | 决策 | 理由 |
|---|---|---|
| D1 | 视觉 = DeepSeek 品牌色 + Claude/Notion 排版 | 用户定稿；暖色、蓝色都试过，DeepSeek 蓝最对味 |
| D2 | 首页固定欢迎界面，无状态切换 | 任务断断续续时切换体验差（用户明确要求） |
| D3 | 新建会话当场选模式 | 避免每次去设置改默认（用户明确要求） |
| D4 | 权限三档 + Full Access 风险确认 | 与 PC 端沙箱模式一致 |
| D5 | 移动端零插件感知 + 可选动作区 | 插件生态差异不进入移动端核心层 |
| D6 | 诚实原则（开发中标注） | 避免虚假功能误导 |
| D7 | 桌面端 命令行双形态兼容 | 同 profile 同 CLI，插件天然兼容 |

## 7. 风险与应对
| 风险 | 应对 |
|---|---|
| 会话配置 API 需要权限边界（改模型 权限影响会话行为） | 写操作要求认证 + 与 PC 端相同的风险确认流程 |
| 通知聚合的事件语义（待回答如何判定） | 已实现：`turn/end` reason.kind=blocked → needs-answer（v2.4 与问询/审批弹窗联动） |
| 动作区契约被第三方插件滥用 | 注册表冲突抛错（Cordis 语义） 文档约定命名空间 |
| 问询/审批桥依赖 apiProxy 私有协议 | 干净降级（不崩、不弹窗），诊断可查，随插件版本跟进——见 09-compatibility |
